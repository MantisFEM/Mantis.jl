Hierarchical ​

Adaptive methods rely on hierarchical constructions: a sequence of levels, each finer than the previous one, where only some objects of each level are active. The Hierarchical module provides the building blocks for such constructions, independently of what the objects are. The same tools are used for hierarchies of elements, in Mantis.Geometry.HierarchicalGeometry, and for hierarchies of basis functions, in Mantis.FunctionSpaces.HierarchicalSpace, for example.

Mantis.Hierarchical Module
julia
module Hierarchical

Utilities related to hierarchies of abstract objects. Includes methods one refinement, scalings between parent and child sets, and information about active objects at each level.

source

Core concepts ​

A hierarchy is built from three ingredients, each with its own section below.

  1. Sets on each level, such as a geometry or a function space. A finer set is obtained from a coarser one through a refinement.

  2. Parent-child relations between the objects of consecutive levels are provided by a scaling.

  3. Active objects on each level, stored in an ActiveInfo.

Consider a 1D geometry with 4 elements on the first level, uniformly refined twice. Some elements are refined (inactive) and replaced by their children:

x inactive
- active

Level 1: |---1---|---2---|xxxxxxx|---4---|
Level 2: |xxx|xxx|xxx|xxx|-5-|-6-|xxx|xxx|

There are two ways active objects, in this case elements, are numbered in Mantis. The level-wise numbering is the numbering of the objects within the set of their level: the active elements above are elements 1, 2 and 4 of level 1, and elements 5 and 6 of level 2. The hierarchical numbering is obtained by concatenating the active objects of all levels: the active elements above are elements 1 to 5. A hierarchical construction is indexed with the hierarchical numbering, while the level-wise numbering is used to evaluate the objects on their level.

Refinement ​

A refinement holds a parent set and a method to produce a child set from it. The child set is created lazily, by calling the refinement with no arguments. This way a refinement can be stored without instantiating the child set, which is useful since in adaptive methods it is not known in advance if a refinement will happen.

Scaling types ​

Mantis has two concrete scalings. A Scaling only provides the relations between parent and child objects, which is enough for geometries. A MatrixScaling additionally stores a scaling matrix, which expresses parent objects as linear combinations of child objects, as needed for function spaces. In this case, the relations are given by the sparsity pattern of the scaling matrix.

Active objects ​

The active objects of each level are stored in an ActiveInfo. Next to the level-wise ids of the active objects, it stores lookup tables to efficiently convert between the level-wise and hierarchical numbering (see Core concepts).

Mantis.Hierarchical.ActiveInfo Type
julia
ActiveInfo

Stores the active objects in a hierarchical construction.

Active objects are grouped by refinement level. Within each level, objects retain their level-wise numbering, while the hierarchical numbering is obtained by concatenating the active objects from all levels.

Besides the level-wise indices, ActiveInfo stores auxiliary lookup tables to efficiently convert between hierarchical and level-wise numbering.

Fields

  • level_ids::Vector{Vector{Int}}: Active level-wise object ids for each level. Useful for fast iteration.

  • level_sets::Vector{Set{Int}}: Set representation of level_ids for fast membership testing.

  • level_lookup::Vector{Dict{Int, Int}}: Maps a level-wise id to its position within level_ids[level].

  • level_cum_num_ids: Cumulative number of active objects per level, used for converting between hierarchical and level-wise numbering.

Outer Constructors

Refining is type unstable

The number of levels is a type parameter of a hierarchy. Since refining the finest level adds a level, the output type of refine and update depends on runtime values. Call such methods behind a function barrier, so that the instability does not propagate.

Example ​

We first build a hierarchical geometry, and then a hierarchical space on top of it.

HierarchicalGeometry ​

We build the hierarchy from Core concepts. We start from a 1D geometry with 4 elements, and a uniform scaling that subdivides each element in 2.

julia
using Mantis
using Mantis.Hierarchical

geo_l1 = Geometry.CartesianGeometry((LinRange(0.0, 1.0, 5),))
scaling = Geometry.scaling_uniform(geo_l1, 2)

The scaling relates each element of level 1 to its children on level 2. For example, element 2 of level 1 is subdivided into elements 3 and 4 of level 2,

julia
get_children(scaling, 2)
3:4

and, conversely, element 3 of level 2 has element 2 of level 1 as parent.

julia
get_parents(scaling, 3)
(2,)

The active elements are elements 1, 2 and 4 of level 1, and elements 5 and 6 of level 2, which gives 5 active elements in total.

julia

HierarchicalSpace ​

We now build a Mantis.FunctionSpaces.HierarchicalSpace on the hierarchical geometry from the previous section. On the first level, we use linear B-splines with regularity. Each finer level is obtained by subdividing the elements in 2 and elevating the degree by 1, both through lazy Refinement. From level 1 to 2, we subdivide and elevate in two separate refinements, while from level 2 to 3, we use a single refinement that composes both.

julia
subdivide(space) = FunctionSpaces.refinement_uniform(space, 2)
elevate(space) = FunctionSpaces.refinement_degree(space, 1)
subdivide_and_elevate = elevate ∘ subdivide

bsp_l1 = FunctionSpaces.create_bspline_space((0.0,), (1.0,), (4,), (1,), (0,))
bsp_l12 = Refinement(bsp_l1, subdivide)()
bsp_l2 = Refinement(bsp_l12, elevate)()
bsp_l3 = Refinement(bsp_l2, subdivide_and_elevate)()
map(FunctionSpaces.get_polynomial_degree, (bsp_l1, bsp_l2, bsp_l3))
(1, 2, 3)

Note that the parametric geometry of the space on each level has to be the geometry on the same level of the hierarchical geometry. This is the case here, since the spaces are subdivided in the same way as the geometries.

Each MatrixScaling composes the scaling matrices of the subdivision and the degree elevation, relating the functions of a level directly to those of the next level. From level 1 to 2, the scaling is given all the intermediate spaces and composes the two scaling matrices itself. From level 2 to 3, there is no intermediate space, so a single scaling method builds it and multiplies both matrices.

julia
elevate_matrix(parent, child) = FunctionSpaces.scaling_matrix_degree(parent, child, 1)
function subdivide_and_elevate_matrix(parent, child)
    subdivided = subdivide(parent)
    subdivide_matrix = FunctionSpaces.scaling_matrix_uniform(parent, subdivided)

    return elevate_matrix(subdivided, child) * subdivide_matrix
end

scaling_1 = MatrixScaling(
    (bsp_l1, bsp_l12, bsp_l2), FunctionSpaces.scaling_matrix_uniform, elevate_matrix
)
scaling_2 = MatrixScaling(bsp_l2, bsp_l3, subdivide_and_elevate_matrix)

Both ways are equivalent

Refining and scaling in separate steps, as from level 1 to 2, or with a single composed function, as from level 2 to 3, gives the same spaces and scaling matrices. Separate steps reuse the existing refinement and scaling methods directly, while a composed function is convenient when the intermediate spaces are not needed.

As a result, only the truncated hierarchical B-splines form a partition of unity.

julia
function is_partition_of_unity(space)
    xi = Points.PointSet((LinRange(0.0, 1.0, 5),))
    for element_id in 1:FunctionSpaces.get_num_elements(space)
        # Values of the basis functions on the element, one column per function.
        values = FunctionSpaces.evaluate(space, element_id, xi)[1][1][1][1]
        if !all(isapprox(1.0), sum(values; dims=2))
            return false
        end
    end

    return true
end
